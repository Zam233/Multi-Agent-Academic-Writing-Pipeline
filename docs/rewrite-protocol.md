# 改写协议与跨章依赖传播（Rewrite Protocol）

> **为什么需要本文件**：此前所有角色都假设任务是"写下一节"。但真实写作里最常见的场景是
> **"第三章推翻了，重写"**——此时没有回退协议，更要命的是：
> **核心论点一变，所有引用过它的小节都该同步，而没人记得住有哪些。**
>
> 纯文本写作没有编译器——改一个论点不会报错。本协议就是那张缺失的**依赖图**：
> 把"论点 → 依赖它的节"显式登记下来，改动时机械算出**影响清单**。
>
> 依据台账：[`templates/LEDGER.md`](../templates/LEDGER.md)、
> 计算脚本：`scripts/ledger-impact.ps1`。

## 一、核心概念：三种台账各管一件事

| 台账 | 管什么 | 回答的问题 |
|---|---|---|
| `STATUS.md` | **进度** | 写到哪了？哪些已审？ |
| `LEDGER.md` | **依赖** | 改了这里，还有哪里要跟着改？ |
| `glossary.md` / `DATA.md` | **口径** | 术语与变量的权威定义是什么？ |

三者缺一不可。**没有 LEDGER.md 时，改写只能靠人回忆**——这正是长文写作最常出的事故。

## 二、依赖类型与传导强度

依赖边分四类，**决定改动要传导多深**（类型由 planner 在规划时登记，steward 维护）：

| 依赖类型 | 含义 | 处理等级 | 建议动作 |
|---|---|---|---|
| `概念依赖` | 本节的论证**以被依赖方的论点为前提** | 1 | **须重写论证**（前提变了，推理链就断了） |
| `证据依赖` | 本节的数据/材料**是被依赖论点的证据** | 1 | **须重核数值与论证** |
| `引用依赖` | 本节**引述**了被依赖方的结论/框架 | 2 | **须修订引述**（改为与新论点一致） |
| `风格依赖` | 仅术语、体例、标题层面的关联 | 3 | **建议复核**（全文检索替换即可） |

> **传导链取最弱一环**：若 S4 依赖 S3（引用依赖）、S3 依赖 C1（概念依赖），
> 则 C1 变动时 S4 的处理等级是 2（取较弱），而非 1。
> 直觉：链上只要有一环只是"引述"，末端就只需改引述，不必重写论证。

## 三、传播机制

```
变更点（论点 C# 或节 S#）
   │ 沿"谁依赖我"反向遍历
   ▼
受影响清单（含 跳数 + 处理等级 + 传导路径 + 建议动作）
   │
   ▼
STATUS.md 标记「需重审」→ 按等级处理 → 回填变更记录
```

**两个度量，含义不同，不可混用**：

- **跳数（Hops）**：从变更点算起的结构距离，反映"多远"；
- **处理等级（Grade）**：由传导链最弱一环决定，反映"要多用力"。

例：改动 C1 后，S2（跳 1，等级 1 重写）、S3（跳 2，等级 2 修订）、S4（跳 3，等级 2 修订）。
**先按等级、再按跳数**处理——先改论证根基，再改引述。

### 执行

```powershell
# 台账自检（悬空引用 / 孤立论点 / 循环依赖）——建议每次会话开始时跑一次
powershell -ExecutionPolicy Bypass -File scripts/ledger-impact.ps1 -Ledger LEDGER.md

# 核心论点被替换：算出谁受影响
powershell -ExecutionPolicy Bypass -File scripts/ledger-impact.ps1 -Ledger LEDGER.md -Changed C2 -ChangeType 替换 -OutPath "_影响清单_最新.md"

# 只看直接依赖
powershell -ExecutionPolicy Bypass -File scripts/ledger-impact.ps1 -Ledger LEDGER.md -Changed C2 -Direct
```

## 四、变更类型（决定重写范围）

| 变更类型 | 含义 | 典型范围 |
|---|---|---|
| `替换` | 原论点被推翻或换成另一个 | 所有依赖方论证需重写 |
| `加强` | 论点不变，证据或表述增强 | 主要影响引述处 |
| `弱化` | 限定条件收紧（"必然"→"在 X 条件下"） | 依赖方中做了强断言处须同步 |
| `删除` | 论点被移除 | 所有依赖方出现**断链**，必须处理 |
| `改名` | 仅术语/名称变化 | 通常风格依赖，全文检索替换 |

> ⚠️ **`弱化` 是最容易被忽略的一类**。把"X 导致 Y"改成"X 与 Y 相关"，
> 表面上只是一处措辞，但所有**据此提出政策建议**的节都失去了强因果支撑——
> 这类问题在盲审里是致命伤，而作者几乎总忘记回头改。

## 五、重写流程（与首次写作共用同一条流水线）

**关键原则：改写不是"重跑 writer"，而是重跑整条流水线。** 因为改动会改变论证前提，
原本已确认的规划可能不再成立。

```
1. 主代理确认变更性质与范围
   ├─ 是「新写」还是「改写」？→ 改写走本协议
   └─ 是「局部修订」还是「推翻重写」？
        · 局部修订（等级 2/3）→ 可直接委派 writer，但须过 auditor
        · 推翻重写（等级 1）  → 必须重跑 planner（规划前提已变）
   ↓
2. 跑 ledger-impact.ps1 得影响清单（先跑自检）
   ↓
3. steward 把受影响节的 STATUS.md 状态改为「需重审」
   ↓
4. 按等级 1 → 2 → 3、同等级内按跳数从近到远，逐个处理：
     等级 1：planner 重新规划 →（用户确认）→ writer 重写 → auditor 重审
     等级 2：writer 修订引述 → auditor 复核
     等级 3：全文检索替换 → consistency 复核
   ↓
5. 每处理完一节，回填 LEDGER.md 的「变更记录」状态
   ↓
6. 全部处理完后，跑 consistency 做一次全文口径复核
     重点：变更后的论点在各处表述是否还一致（改了一处忘了另一处）
   ↓
7. 变更记录状态改为「已完成」；steward 写 session-handoff.md
```

### 硬性闸门（与首次写作一致，不得因"只是改一下"而放松）

- **等级 1 的节必须重跑 planner 并经用户确认**——不得让 writer 直接凭"新论点"改，
  因为改动的连锁影响需要重新规划才能看清；
- **任何重写都必须过 auditor**——"我自己改的我知道改对了"是幻觉；
- **改写后必须重跑一致性检查**——这是发现"改了 A 忘了 B"的最后一道网。

## 六、登记纪律（决定本协议是否有效）

依赖台账的价值完全取决于**登记是否完整**。三条硬规则：

1. **登记时机**：planner 完成规划时，**必须**把本次新增的论点（C#）与依赖边登记进 `LEDGER.md`。
   漏登 = 未来改写时该处不会被传播到，等于没有台账。
2. **粒度**：只登记**实质性依赖**（论证前提、证据、引述），不登记"同属一章"这类形式关联。
   登记过滥会让影响清单失去信噪比，反而被忽略。
3. **同步**：`STATUS.md` 的节 ID 必须与 `LEDGER.md` 的节 ID 一致（都用 S1、S2…），
   否则两张表无法互相校验。

> **steward 的自检职责**：每次会话开始、以及每次登记变更后，跑一次
> `ledger-impact.ps1` 的自检模式，确认无悬空引用、无孤立论点（=漏登记）、无意外循环依赖。

## 七、已知局限（如实说明）

1. **台账只覆盖显式登记的依赖**。语义层面的隐含关联（"虽然没引用，但两节在讨论同一件事"）
   无法机械发现。故影响清单末尾始终附一句提示：实质改动仍建议 planner 做语义复核。
2. **循环依赖被标为警告而非错误**。学术写作中两节互相引述是**正常**的
   （如方法章与结果章相互参照），故脚本只提示"请确认是否合理"，不阻断。
3. **传播是保守的**（宁多勿少）。它可能列出实际不需要改的节；
   漏掉需要改的节代价远高于多列一个——**由人判断，不由脚本删减**。
